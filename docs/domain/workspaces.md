## Workspace Visibility & Scope (`PUBLIC`, `PRIVATE`, `PERSONAL`)

- **Personal Workspace ("My Workspace", `scope = 'personal'`):** Every user gets exactly one personal workspace, enforced in PostgreSQL by the partial unique index `uq_workspaces_personal_owner` and provisioned lazily via `WorkspaceRepository.ensure_personal_workspace`. Personal workspaces are strictly single-user: `WorkspaceAuth.authorize`, `WorkspaceAuth.authorize_write`, `is_workspace_manager`, and unscoped queries (`UnifiedGalleryRepository`, `SourceAssetRepository`, `TagsRepository`, `AdminRepository`) never expose another user's personal workspace, including to global `ADMIN` users. Cross-workspace moves (`bulk_move`) out of a personal workspace are rejected (`400`); items in a personal workspace remain isolated unless explicitly copied (`bulk_copy`). In the Angular client (`WorkspaceSwitcherComponent` + `WorkspaceStateService`), initial navigation defaults to `"My Workspace"` unless overridden by `?workspaceId=` or a per-tab, user-scoped `sessionStorage` selection (`cs_active_workspace_id:<userKey>`).
- **Org-Wide Shared Workspace (`scope = 'public'`):** Visible to all authenticated users. Regular users receive effective role `EDITOR`; global `ADMIN` users receive `ADMIN` and act as workspace managers. `WorkspaceService.invite_user_to_workspace` rejects invitations targeting `PUBLIC` or `PERSONAL` workspaces.
- **Team Shared Workspace (`scope = 'private'`):** Visible only to explicit members (`workspace_members`) and global `ADMIN` users. User workspace lists return `[personal, ...private, ...public]` with `current_user_role` populated via `resolve_effective_role`.

## Shared-Workspace Role Parity (`Owner / Admin / Editor / Viewer`)

`backend/src/workspaces/workspace_auth_guard.py` is the single source of truth for workspace authorization (`authorize`, `authorize_write`, `resolve_effective_role`, `is_workspace_manager`):

- **`OWNER` / `ADMIN` (plus global `ADMIN` on shared workspaces):** Full management rights (`is_workspace_manager == True`), including inviting/managing workspace members (except assigning `OWNER` via invitation), managing folders and subtrees regardless of item creator, managing workspace Brand Guidelines, deleting/moving any workspace gallery item or folder, and editing/deleting workspace tags.
- **`EDITOR`:** Read and write access (`authorize_write` passes), creator-scoped for folder updates/deletes/moves (`ensure_can_manage_folder`, `subtree_has_foreign_content`), tag updates/deletes, and gallery `bulk_delete` / `bulk_move`. Cannot invite members or mutate Brand Guidelines.
- **`VIEWER`:** Strictly read-only in `PRIVATE` workspaces. All shared-workspace write endpoints (`POST`/`PUT`/`PATCH`/`DELETE` across folders, tags, source assets, gallery mutations, and timeline create/update/delete) call `authorize_write` and reject `VIEWER`s with HTTP `403`, while generation and timeline-render routes call read-context `authorize` and write outputs privately into the caller's personal workspace. Frontend gallery, folder, tag, and lightbox controls mirror these permissions via `WorkspaceStateService.canEditWorkspace` and `WorkspaceStateService.canManageWorkspace`.

## Brand Guidelines (Shared Workspaces Only)

- Brand Guidelines belong strictly to shared (`PUBLIC` or `PRIVATE`) workspaces (`400` if targeting a `PERSONAL` workspace). Management (`generate_signed_upload_url`, create, update, delete) requires `is_workspace_manager`; reads require workspace membership (`authorize`).

## Shared Timelines & Private Clip Access

- **Reading a Shared Timeline (`GET /api/workbench/timelines/{id}`, `GET /api/workbench/timelines`):** Requires read access (`authorize`) on the timeline's workspace (`timeline.workspace_id`, failing closed with `403` when missing - never falling back to a fabricated workspace ID). Once authorized, `enrich_timeline` signs all clip URLs so any workspace member can open and inspect a shared timeline even when it contains clips originally created in another member's private workspace.
- **Saving or Rendering a Timeline (`POST /timelines`, `PUT /timelines/{id}`, `POST /render`):** Enforces both `authorize_write` on timeline creates/updates (or read-context `authorize` on render, which routes outputs privately via `resolve_generation_context`) and `ensure_can_reference_inputs` across every referenced `MediaItem` and non-`SYSTEM` `SourceAsset` (video clips, first/last frame references, and audio clips), plus `_ensure_storyboard_in_workspace` when a `storyboard_id` is supplied. A colleague who lacks direct read access to an author's private clip is rejected with HTTP `403` before any database write or background render job is queued.

## Schema Rollback (`c8f3a1b2d4e5`)

- Downgrading revision `c8f3a1b2d4e5` drops the personal-workspace unique index (`uq_workspaces_personal_owner`) after cleaning up `scope = 'personal'` rows: empty `personal` workspaces (with no `media_items`, `source_assets`, `folders`, `tags`, `brand_guidelines`, `storyboards`, or `timelines`) are deleted, while non-empty `personal` workspaces are converted to `scope = 'private'` with `owner` membership preserved in `workspace_members` so pre-feature versions boot cleanly without data loss. Because downgraded rows have `scope = 'private'`, they become visible to global `ADMIN` users on pre-feature code, and re-upgrading `c8f3a1b2d4e5` lazily provisions a fresh `'My Workspace'` personal workspace per user rather than auto-converting downgraded `private` workspaces back to `personal`.

## Private-First Generation, Upload, and Loop Routing

- **Private-First Output Routing (`resolve_generation_context`):** Generation and render endpoints (`ImagenService`, `VeoService`, `AudioService`, `WorkbenchService.render_timeline_by_id`, and upload-upscale) authorize read access on `requested_workspace_id` and any distinct `context_workspace_id`, lazily provision the caller's personal workspace via `WorkspaceRepository.ensure_personal_workspace` whenever a shared workspace is targeted, route `output_workspace_id = personal_ws.id` while preserving `brand_workspace_id = context_workspace_id or requested_workspace_id`, and ignore shared `folder_id` values for personal outputs after verifying folder read access. `WorkflowService.batch_execute_workflow` likewise routes batch CSV `gs://` `SourceAsset` ingestion via `resolve_generation_context(..., resolve_folder=False)` while preserving the caller's `workspace_id` on the submitted workflow run. In background video jobs, `VeoService._process_video_in_background` re-verifies referenced inputs in the worker against both `output_workspace_id` and `context_workspace_id`.
- **Cross-Workspace Input Authorization (`ensure_can_reference_inputs`) & DTO Strictness:** Imagen, Veo, VTO, Video Concatenation, and Upload-Upscale validate every referenced `MediaItem` and non-`SYSTEM` `SourceAsset` against the caller's readable workspaces (`authorize` or `PUBLIC` read), allowing users to browse shared workspace assets and generate derivatives privately. Only `CreateImagenDto`, `CreateVeoDto`, and `VtoDto` accept optional `context_workspace_id` (`contextWorkspaceId` for shared brand-guideline lookup and worker input verification); `CreateAudioDto`, `ConcatenateVideosDto`, and `RenderTimelineRequest` enforce `extra="forbid"` without `context_workspace_id`, so frontend callers (`AudioComponent`, `VideoComponent` concatenation, and `WorkbenchComponent` render) must omit it.
- **Workflow Loop Item Authorization (`WorkflowsExecutorService._resolve_linked_items`):** When resolving gallery inputs for workflow loops, `UnifiedGalleryRepository.lookup_linked_loop_item_workspaces` maps each referenced `MediaItem` or `SourceAsset` ID to its owning workspace and `WorkspaceAuth.authorize` confirms caller read access before exposing items to workflow execution.
- **Frontend Upload, Cropper, Picker, and Workbench Routing:** `WorkspaceStateService.getTargetWorkspaceParam()` returns `{workspaceId: personal ?? active}` for payloads without `contextWorkspaceId` (`AudioComponent`, `UpscaleComponent`), while `WorkspaceStateService.getReferencedGenerationWorkspaceParams()` returns `{workspaceId: personal ?? active, contextWorkspaceId}` for Imagen, Veo, and VTO. Direct drops, cropper saves, and `ImageSelectorComponent` uploads route to the personal workspace, whereas `MediaGalleryComponent` direct and Drive uploads target `effectiveWorkspaceId` (the currently browsed workspace and `currentFolderId`, guarded by `authorize_write` in the backend). `WorkbenchComponent` saves preserve `loadedTimelineWorkspaceId` when updating an existing shared timeline, route new manual timelines to the personal workspace, and fail closed without creating or updating if no workspace is available.

## Revision Stacks & Workflow Loop Pinning

- **Stack Grouping & Concurrency Locking (`backend/src/galleries/revision_lineage.py`):** Iterating on an existing `MediaItem` (`parent_media_item_id`, Imagen/VTO/upscale input links, or Veo `VIDEO_EXTENSION_SOURCE` / `VIDEO_EXTENSION_CHUNK` / `CONCATENATION_SOURCE`) groups the new placeholder under `COALESCE(revision_root_id, id)` inside the caller's personal workspace. `resolve_revision_lineage` acquires `SELECT ... FOR UPDATE` (`include_deleted=True`) on the stack root before computing `MAX(revision_number) + 1`, so concurrent edits cannot reuse numbers and soft-deleting `v1` keeps `v2..vN` grouped. When an explicit destination folder resolves differently from the existing stack's latest active folder, iteration starts a fresh stack (`RevisionLineage(None, None, 1, None)`) rather than hiding earlier takes across folders.
- **Colleague Remixes Stay Separate:** Iterating on a colleague's shared item returns `RevisionLineage(None, None, 1, None)`, starting a brand-new stack in the caller's personal workspace.
- **Gallery Collapse & Shared-Workspace Scope:** `UnifiedGalleryRepository.query` collapses active completed stacks to their latest completed take (`revision_number DESC, id DESC`, backed by `ix_media_items_stack_root_active`, shared via `latest_completed_take_predicate()`). `RevisionService.get_revisions` exposes full stack takes only for `PERSONAL` workspaces (outside `PERSONAL`, returns only `[item]`). Completed stack counts in folders (`COUNT(DISTINCT COALESCE(revision_root_id, id))`), copy deduplication (`merge_folders(is_copy=True)`, `copy_folder_to_workspace`), `FolderRepository.move_media_items`, and `GalleryService.bulk_move` co-locate stacks uniformly via `stack_root_expr()` and `latest_completed_take_predicate()`.
- **Workflow Loop Pinning:** `UnifiedGalleryRepository.list_folder_loop_items` filters `is_latest_revision IS TRUE` so folder loops pick the latest completed take of each stack. Conversely, specific linked-item lookups (`filter_linked_loop_items` and `lookup_linked_loop_item_workspaces`) **never** filter by `is_latest_revision`: a saved workflow step linked to `v1` stays pinned to `v1` even after newer completed or in-progress takes (`v2`) are added to the stack.
